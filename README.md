# tapka

Менеджер переносимых пакетов для Windows на .NET 11. Tapka читает рецепты `packages/<id>/config.json` из локального снимка каталога. Новые установки хранятся в `%LOCALAPPDATA%\tapka\packages\<id>\<version>`, а команды явно установленных пакетов доступны в PATH через shim-файлы в `%LOCALAPPDATA%\tapka\shims\public`. [Каталог Tapka](https://github.com/Tapka-pm/packages)

## Установка tapka

В Windows PowerShell или PowerShell 7 выполните:

```powershell
irm https://raw.githubusercontent.com/Tapka-pm/tapka/master/install.ps1 | iex
```

В CMD выполните:

```cmd
powershell.exe -NoProfile -NonInteractive -Command "$ErrorActionPreference='Stop'; irm https://raw.githubusercontent.com/Tapka-pm/tapka/master/install.ps1 | iex" && for %I in (tapka.exe) do @if /i not "%~$PATH:I"=="%LOCALAPPDATA%\tapka\shims\public\tapka.exe" set "PATH=%LOCALAPPDATA%\tapka\shims\public;%PATH%"
```

Сразу после установки выполните `tapka --help` в том же терминале. Нужны Windows x64 и интернет. Установщик работает от текущего пользователя и ставит переносимые .NET 11 и PowerShell 7 в дерево Tapka.

Можно также скачать `tapka-setup-win-x64.exe` из [последнего релиза](https://github.com/Tapka-pm/tapka/releases/latest) и открыть его двойным щелчком. После этого запустите новый терминал.

## Сборка

Для сборки нужны .NET 11 SDK и Visual Studio Build Tools с рабочей нагрузкой «Разработка классических приложений на C++» (MSVC x64 и Windows SDK). Скрипт ищет .NET SDK в `artifacts\tools` и `PATH`; параметр `-DotNet` принимает путь к `dotnet.exe`. Для компилятора shim сначала используется `cl.exe` из `PATH`, затем поиск через `vswhere.exe` и инициализация MSVC x64 через `vcvarsall.bat`. [.NET 11 SDK](https://dotnet.microsoft.com/download/dotnet/11.0), [Visual Studio Build Tools](https://visualstudio.microsoft.com/visual-cpp-build-tools/)

| Команда | Результат |
| --- | --- |
| `.\build.ps1 -Version 0.1.0` | `artifacts\release\tapka-win-x64.zip` и `artifacts\release\tapka-setup-win-x64.exe` |
| `.\build.ps1 -Test` | `artifacts\test\tapka.exe` |
| `.\build.ps1 -Test -Target Setup -Version 0.1.0` | `artifacts\test\tapka-setup-win-x64.exe` |

Клиент и установщик подключают `src/shim/shim.targets`: MSBuild автоматически компилирует `launcher.c` и встраивает shim как ресурс `tapka.shim.exe`. Обычные команды `dotnet build src/tapka/tapka.csproj` и `dotnet publish src/setup/setup.csproj -c Release` работают без предварительного запуска `build.ps1` и передачи пути к shim. Нативный бинарник находится в `artifacts\build\shim\<Configuration>\x64\shim.exe`; он пересобирается при изменении исходника, скрипта компилятора или targets. Скрипт `build.ps1` выбирает параметры публикации и упаковывает релиз.

Клиент в релизном ZIP использует .NET из приватной зависимости `dotnet-runtime-11`. При запуске tapka её shim передаёт путь к runtime через `DOTNET_ROOT` и `DOTNET_ROOT_X64`. Тестовый клиент содержит собственную среду выполнения, чтобы его можно было запустить напрямую.

## Публикация

Push стабильного тега формата `vX.Y.Z` запускает workflow Release tapka. До push тега загрузите изменения ветки `master` и подготовьте изменения каталога в ветке `master` репозитория `Tapka-pm/packages`. Настройте в GitHub Actions secret `PACKAGES_TOKEN` с правом Contents: read and write только для репозитория каталога. У токена должен быть доступ к записи в `master`.

Workflow собирает и тестирует оба файла, загружает их в черновик GitHub Release и добавляет точный URL и SHA-256 клиентского ZIP в каталог. Затем он публикует Release и обновляет алиас `latest`, если этот выпуск новее. При сбое перезапустите workflow того же тега. Уже загруженные файлы сохраняются.

Установщик из каждого релиза запрашивает версию своего тега. Каталог сохраняет выпущенные версии tapka, чтобы старые установщики продолжали работать.

## Установка пакетов

```powershell
tapka install git
tapka install dotnet-runtime@lts
tapka install powershell
```

`install` принимает имя пакета, `имя@версия` или `имя@алиас`. В `versions` рецепт перечисляет актуальные релизы поддерживаемых линеек и их алиасы, например `lts` и `sts`. Без суффикса используется `latest`. Повторный вызов с тем же алиасом берёт его актуальную цель из рецепта. Предыдущие релизы доступны в истории Git.

Tapka устанавливает зависимости первыми и проверяет SHA-256 или SHA-512 скачанных файлов. Рецепт задаёт `install.archive`, `install.script` или оба поля. Если заданы оба, Tapka сначала распаковывает архив, затем запускает скрипт и публикует пакет после проверки объявленных команд. Скрипт получает проверенный файл в `-Installer` и временный каталог пакета в `-Destination`. При наличии `install.archive` в этом каталоге уже лежат распакованные файлы. Для скриптов используется PowerShell 7. Если подходящий `pwsh.exe` не найден, Tapka устанавливает `powershell` из того же каталога.

Рецепт задаёт формат в `install.archive` независимо от имени файла в URL. Допустимые значения — `zip`, `tar`, `tar.gz`, `7z`, `rar` и `tar.xz`. Первые три формата обрабатываются средствами .NET. Для остальных Tapka при первой необходимости устанавливает `7zip` из выбранного каталога. Для его первоначальной распаковки используются `7zr` и PowerShell 7. Tapka сохраняет инструменты для следующих установок. Автоматическая установка архиватора не добавляет его команды в PATH пакета или пользователя. Чтобы открыть `7z.exe` в пользовательском PATH, выполните `tapka install 7zip`. Архивы с паролем и многотомные архивы не поддерживаются.

Команды зависимостей доступны скрипту установки и процессам пакета через приватные shims. Tapka добавляет их каталог в начало PATH дочернего процесса. Чтобы открыть команды зависимости в пользовательском PATH, явно установите её через `tapka install <id>`. Если версия уже сохранена, Tapka повторно использует её файлы. Это касается и PowerShell, установленного для запуска скриптов.

В поле `dependencies` можно указать ID или объект с картой `rename`.

```json
"dependencies": [
  "powershell",
  { "id": "git", "rename": { "git": "vendor-git" } }
]
```

В этом примере Tapka создаёт `vendor-git.exe` вместо `git.exe` в каталоге shims зависимостей пакета. Остальные команды сохраняют свои имена. Имена сравниваются без учёта регистра, суффикс `.exe` можно опустить. Команды транзитивных зависимостей доступны под исходными именами. Чтобы переименовать такую команду, укажите её пакет напрямую в `dependencies`. Если несколько зависимостей предоставляют одно итоговое имя, установка завершается ошибкой.

Откройте новый сеанс PowerShell или `cmd.exe` из меню «Пуск», чтобы оболочка получила обновлённый пользовательский `PATH`. Если другая программа с тем же именем стоит выше в `PATH`, Tapka напечатает путь к ней.

Публичный shim читает активную конфигурацию при запуске. Приватный shim использует пути, выбранные для его поколения. Все пути разрешаются относительно корня Tapka. При переносе всего дерева обновите путь к `shims\public` в пользовательском `PATH`.

Параметр `--repository` принимает базовый HTTPS URL каталога или путь к локальному клону. Сторонний HTTPS-каталог публикует `repository.zip` с деревом `packages/` в корне архива. Для соседнего каталога `packages` выполните из папки клиента:

```powershell
tapka install git --repository ..\packages
```

Даже при использовании локального каталога Tapka скачивает дистрибутив по HTTPS из URL в рецепте. Используйте каталоги, которым доверяете, поскольку их рецепты могут запускать скрипты установки.

## Обновление каталога и пакетов

```powershell
tapka update
tapka upgrade
tapka upgrade git powershell
```

`update` обновляет снимки официального каталога и источников установленных пакетов. `tapka update --repository <source>` обновляет один источник. `install` и `upgrade` автоматически загружают снимок, если его нет или ему исполнилось 24 часа. С `TAPKA_NO_AUTO_UPDATE=1` снимки обновляются только через `update`. При неудачной загрузке Tapka сохраняет предыдущий снимок и сообщает об ошибке.

`upgrade` без аргументов обновляет все установленные пакеты, включая зависимости, служебные инструменты и саму Tapka. Список ID ограничивает обновление выбранными пакетами и нужными им зависимостями. По умолчанию Tapka использует сохранённый источник каждого пакета. `--repository` переопределяет его на время операции. Укажите его для старых пакетов, источник которых неизвестен.

Алиасы, например `latest` и `lts`, следуют за своей целью в каталоге, даже если она вернулась к предыдущему релизу. Точная версия закрепляет пакет. Новые установки Tapka через установщик отслеживают `latest`. Чтобы переключить ранее закреплённую Tapka на `latest`, выполните `tapka install tapka@latest`.

Новые процессы стартуют через shims активной версии. Уже запущенные процессы сохраняют прежние бинарники и зависимости. Tapka хранит старые версии на диске и сохраняет прежние пути установок после миграции. Если Windows блокирует перенос старого shim при первой миграции, завершите процессы, запущенные через указанный shim, и повторите команду.

## Просмотр установленных пакетов

```powershell
tapka list
tapka list dotnet
tapka list --explicit
tapka info dotnet-runtime-11
Set-Location (tapka path git)
```

`list` показывает все пакеты Tapka, в том числе зависимости и служебные инструменты. `--explicit` оставляет пакеты, которые запросили явно. `info` показывает выбранный селектор, установленную версию, путь, источник, команды и зависимости в обе стороны. Эти команды работают без сети.

Текущее состояние хранится в `%LOCALAPPDATA%\tapka\installed.db`. При первом обращении Tapka переносит сведения из старых файлов `.tapka-*` и оставляет их на месте. Поля, которых в старом формате не было, отображаются как неизвестные. При переносе дерева Tapka скопируйте вместе с пакетами и базу данных.

## Тестовая установка

```powershell
.\build.ps1 -Test
$testRoot = Join-Path $PWD 'artifacts\test-data\manual'
.\artifacts\test\tapka.exe install git --root $testRoot
$env:Path = (Get-Content "$testRoot\user-path.txt" -Raw) + ';' + $env:Path
git --version
```

Тестовый exe требует абсолютный путь в `--root` и помещает пакет и shim в этот каталог. Он хранит тестовый `PATH` в файле `user-path.txt`. Добавление пути в примере применяется к текущему сеансу PowerShell.

`.\test.ps1` запускает тестовый exe с новым каталогом, проверяет установку Git и повторный вызов с установленной версией через `@`. Он также проверяет команды Git, передачу аргументов и кода завершения в новых процессах PowerShell и `cmd.exe`. Сценарию нужен доступ к GitHub для скачивания PortableGit. Для проверки локальных рецептов запустите `.\test.ps1 -Repository ..\packages`.

После сборки `build.ps1 -Test` команда `dotnet run --project tests/Dependencies` проверяет приватные зависимости, переименование и откат на локальных тестовых рецептах без скачивания из интернета. Для неё нужны .NET 11 SDK и PowerShell 7.

Команда `dotnet run --project tests/Dependencies -- --upgrades artifacts/test/tapka.exe` проверяет кеширование, обновление и повторное использование версий, работающие процессы и самообновление через shim на локальных тестовых файлах.

Скрипт `.\test-archives.ps1` собирает тестовый клиент и прогоняет `tapka install` для ZIP, TAR, TAR.GZ, 7z, RAR и TAR.XZ в отдельном временном каталоге. Он проверяет содержимое пакетов, коды возврата, повторную установку, видимость команд, установку 7-Zip по требованию и откат при ошибке.

Для полного прогона скрипт скачивает недостающие дистрибутивы `7zr`, `7zip` и `powershell` для архитектуры Windows в `artifacts\archive-upstream` и сверяет SHA-256 по рецептам. Ключ `-Offline` запускает все сценарии из кеша, а `-BuiltInOnly` проверяет ZIP, TAR и TAR.GZ без этих дистрибутивов. Параметры `-Repository` и `-Assets` позволяют указать другой каталог рецептов или кеш. Сам тестовый клиент получает файлы локально и пишет PATH только в тестовый корень.

Из каталога клиента запустите `dotnet test tests/Shim.Tests`, чтобы проверить генерацию бинарника, запуск команд, окружение и перенос дерева. Проект автоматически собирает оптимизированный shim и тестовый exe через MSVC. При первой сборке тестов нужен доступ к NuGet.

`.\test-setup.ps1` проверяет AOT-установщик из `artifacts\test` с клиентским релизным ZIP. Используйте одну и ту же версию при сборке ZIP и установщика. Тест устанавливает обе зависимости и клиент в изолированный каталог, запускает публичный shim и проверяет повторную установку и откат при неверном хеше.
