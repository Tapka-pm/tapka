# tapka

Менеджер переносимых пакетов для Windows на .NET 11. Tapka читает рецепты `packages/<id>/config.json` из официального каталога. Установленные пакеты хранятся в `%LOCALAPPDATA%\tapka\packages`, а команды явно установленных пакетов доступны в PATH через shim-файлы в `%LOCALAPPDATA%\tapka\shims\public`. [Каталог Tapka](https://github.com/Tapka-pm/packages)

## Сборка

Для сборки нужны .NET 11 SDK и Visual Studio Build Tools с рабочей нагрузкой «Разработка классических приложений на C++» (MSVC x64 и Windows SDK). Скрипт ищет .NET SDK в `artifacts\tools` и `PATH`; параметр `-DotNet` принимает путь к `dotnet.exe`. Для компилятора shim сначала используется `cl.exe` из `PATH`, затем поиск через `vswhere.exe` и инициализация MSVC x64 через `vcvarsall.bat`. [.NET 11 SDK](https://dotnet.microsoft.com/download/dotnet/11.0), [Visual Studio Build Tools](https://visualstudio.microsoft.com/visual-cpp-build-tools/)

| Команда | Результат |
| --- | --- |
| `.\build.ps1` | `artifacts\release\tapka.exe` |
| `.\build.ps1 -Test` | `artifacts\test\tapka.exe` |

Скрипт собирает x64-клиент со встроенной средой выполнения .NET. Клиент выбирает `x64` или `arm64` в рецепте по архитектуре Windows. Общий проект MSBuild собирает нативный шаблон shim в `artifacts\build\shim\Release\x64\shim.exe` для клиента и тестов.

## Установка пакетов

```powershell
.\artifacts\release\tapka.exe install git
.\artifacts\release\tapka.exe install dotnet-runtime@lts
.\artifacts\release\tapka.exe install powershell
```

`install` принимает имя пакета, `имя@версия` или `имя@алиас`. В `versions` рецепт перечисляет актуальные релизы поддерживаемых линеек и их алиасы, например `lts` и `sts`. Без суффикса используется `latest`. Для явно запрошенного пакета Tapka сохраняет выбранный селектор в `.tapka-selector`, а установленный номер версии в `.tapka-version`. Повторный вызов с тем же алиасом берёт его актуальную цель из рецепта. Предыдущие релизы доступны в истории Git.

Tapka устанавливает зависимости первыми, проверяет SHA-256 или SHA-512 скачанных файлов и распаковывает архив либо запускает PowerShell-скрипт из рецепта. Для скриптов используется PowerShell 7. Если подходящий `pwsh.exe` не найден, Tapka устанавливает `powershell` из того же каталога.

Рецепт задаёт формат в `install.archive` независимо от имени файла в URL. Допустимые значения — `zip`, `tar`, `tar.gz`, `7z`, `rar` и `tar.xz`. Первые три формата обрабатываются средствами .NET. Для остальных Tapka при первой необходимости устанавливает `7zip` из выбранного каталога. Для его первоначальной распаковки используются `7zr` и PowerShell 7. Tapka сохраняет инструменты для следующих установок. Автоматическая установка архиватора не добавляет его команды в PATH пакета или пользователя. Чтобы открыть `7z.exe` в пользовательском PATH, выполните `tapka install 7zip`. Архивы с паролем и многотомные архивы не поддерживаются.

Команды зависимостей доступны скрипту установки и процессам пакета через `shims\deps\<id>`. Tapka добавляет этот каталог в начало PATH дочернего процесса. Чтобы открыть команды зависимости в пользовательском PATH, явно установите её через `tapka install <id>`. Tapka повторно использует файлы, если нужная версия уже установлена. Это касается и PowerShell, установленного для запуска скриптов.

В поле `dependencies` можно указать ID или объект с картой `rename`.

```json
"dependencies": [
  "powershell",
  { "id": "git", "rename": { "git": "vendor-git" } }
]
```

В этом примере Tapka создаёт `vendor-git.exe` вместо `git.exe` в каталоге shims зависимостей пакета. Остальные команды сохраняют свои имена. Имена сравниваются без учёта регистра, суффикс `.exe` можно опустить. Команды транзитивных зависимостей доступны под исходными именами. Чтобы переименовать такую команду, укажите её пакет напрямую в `dependencies`. Если несколько зависимостей предоставляют одно итоговое имя, установка завершается ошибкой.

Откройте новый сеанс PowerShell или `cmd.exe` из меню «Пуск», чтобы оболочка получила обновлённый пользовательский `PATH`. Если другая программа с тем же именем стоит выше в `PATH`, Tapka напечатает путь к ней.

Каждый shim хранит пути к программе и каталогу зависимостей внутри своего `.exe`. Пути разрешаются относительно корня Tapka. Если переносите всё дерево установки, обновите путь к `shims\public` в пользовательском `PATH`. Отдельные shims должны оставаться в дереве установки. Старую установку с файлами `.exe.target` нужно пересоздать и заново установить нужные пакеты.

Параметр `--repository` принимает базовый HTTPS URL каталога или путь к локальному клону. Для соседнего каталога `packages` выполните из папки клиента:

```powershell
.\artifacts\release\tapka.exe install git --repository ..\packages
```

Даже при использовании локального каталога Tapka скачивает дистрибутив по HTTPS из URL в рецепте. Используйте каталоги, которым доверяете, поскольку их рецепты могут запускать скрипты установки.

## Тестовая установка

```powershell
.\build.ps1 -Test
$testRoot = Join-Path $PWD 'artifacts\test-data\manual'
.\artifacts\test\tapka.exe install git --root $testRoot
$env:Path = (Get-Content "$testRoot\user-path.txt" -Raw) + ';' + $env:Path
git --version
```

Тестовый exe требует абсолютный путь в `--root` и помещает пакет и shim в этот каталог. Он хранит тестовый `PATH` в файле `user-path.txt`. Добавление пути в примере применяется к текущему сеансу PowerShell.

`.\test.ps1` запускает тестовый exe с новым каталогом, проверяет установку Git и повторный вызов с установленной версией через `@`. Он также проверяет команды Git, передачу аргументов и кода завершения в новых процессах PowerShell и `cmd.exe`. Сценарию нужен доступ к GitHub для скачивания PortableGit. Для проверки локальных рецептов запустите `.\test.ps1 -Repository ..\packages`.

После сборки `build.ps1 -Test` команда `dotnet run --project tests/Dependencies` проверяет приватные зависимости, переименование и откат на локальных тестовых рецептах без скачивания из интернета. Для неё нужны .NET 11 SDK и PowerShell 7.

Скрипт `.\test-archives.ps1` собирает тестовый клиент и прогоняет `tapka install` для ZIP, TAR, TAR.GZ, 7z, RAR и TAR.XZ в отдельном временном каталоге. Он проверяет содержимое пакетов, коды возврата, повторную установку, видимость команд, установку 7-Zip по требованию и откат при ошибке.

Для полного прогона скрипт скачивает недостающие дистрибутивы `7zr`, `7zip` и `powershell` для архитектуры Windows в `artifacts\archive-upstream` и сверяет SHA-256 по рецептам. Ключ `-Offline` запускает все сценарии из кеша, а `-BuiltInOnly` проверяет ZIP, TAR и TAR.GZ без этих дистрибутивов. Параметры `-Repository` и `-Assets` позволяют указать другой каталог рецептов или кеш. Сам тестовый клиент получает файлы локально и пишет PATH только в тестовый корень.

Из каталога клиента запустите `dotnet test tests/Shim.Tests`, чтобы проверить генерацию бинарника, запуск команд, окружение и перенос дерева. Проект автоматически собирает оптимизированный shim и тестовый exe через MSVC. При первой сборке тестов нужен доступ к NuGet.
